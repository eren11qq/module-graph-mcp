# ADR 0001: evals maxBytes 是 CI 红线契约

- 状态：已接受（2026-08-31）
- 关联：信任闭环路线图 PR-2；词条见 `CONTEXT.md`（EvalTask / probe / 信任门）

## 背景

路线图把分工定成「AI 负责 speed，module-graph 负责 trust」。测试只证明行为对，
不证明**响应经济性**：一个 MCP 工具的响应可以从 300B 无声地膨胀到 300KB——
行为测试全绿，agent 的上下文窗口和 token 账单却在流血。逐任务冷启动的 evals
探针（`npm run evals`）已经记录了每次响应的字节数，但"记录"只是观测。

## 决策

maxBytes（与 maxMs）是**硬契约**，不是仪表盘数字：

1. 每条 EvalTask 写死 `maxBytes` 与 `maxMs`；探针响应超限 → 该任务红 →
   `npm run evals` 退出码非零 → CI 第四步红。
2. 初始值 = 本地实测 p95 × 1.5 向上取整；CI（ubuntu）跑一轮后以 CI 值为准回写。
3. runner 无论绿红，始终记录 p50/p95（ms 与 bytes 两列）——契约收紧不牺牲观测。
4. 改动只能**收紧或重新校准**，不能为让红变绿而放宽；放宽必须连带探针与文档
   （CLAUDE.md evals 纪律）同一 PR，并说明动机。

## 后果

- **难逆**：一旦 CI 把响应体积当红线，所有依赖"大响应无所谓"的隐式假设都会在
  这里现形；回退意味着把信任闭环降级回观测——这是产品定位的倒退，不是参数调整。
- **意外**：CI 会被响应体积打红——哪怕全部功能测试通过。这是设计意图：体积
  回归在开发机上就该被看见，而不是等用户抱怨 agent 变贵。
- **权衡：观测 vs 契约**：只记录（观测）永远安全但从不阻止退化；写死门槛
  （契约）偶尔误伤（合法的新字段挤爆旧预算，如 begin_review 内嵌 playbook）。
  我们选契约，并用「预算变更必须与探针同 PR」来吸收误伤——预算是接口的一部分，
  不是调参。
